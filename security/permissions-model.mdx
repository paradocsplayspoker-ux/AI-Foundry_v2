AI Forge uses a layered security model to give you precise control over what each agent can do. Every permission check is enforced on the server — agents cannot override or bypass restrictions by claiming elevated access on the client side. This means that even if an agent's response asserts it has a capability, the server will reject any action not explicitly permitted by your configuration.

## Per-Agent Permission Flags

Each agent in your project is assigned a set of permission flags. These flags determine exactly which categories of actions the agent may perform. You configure these flags when you add an agent to a project or edit an existing agent's settings.

| Flag | What It Controls |
|---|---|
| `read_files` | Read any file within the project root |
| `write_files` | Create or modify files within the project root |
| `delete_files` | Permanently delete files within the project root |
| `execute_commands` | Run terminal commands inside the project sandbox |
| `install_packages` | Install packages via package managers (e.g. npm, pip) |
| `network_access` | Make outbound HTTP/S requests to external services |

<Warning>
**SAFE_MODE blocks all destructive operations** — including `delete_files`, `execute_commands`, and `install_packages` — for every agent in the project, regardless of their individual flag settings. Use SAFE_MODE whenever you are working with untrusted agents or evaluating a new agent's behavior for the first time.
</Warning>

Granting only the permissions an agent truly needs is the best way to limit the blast radius of an unexpected or erroneous action. For example, a code-review agent typically needs only `read_files` — there is no reason to grant it `delete_files` or `execute_commands`.

## Project-Level Execution Modes

In addition to per-agent flags, every project has an execution mode that governs how and when agents may apply changes. The execution mode acts as a project-wide override on top of individual agent permissions.

<Accordion title="ASK_BEFORE_CHANGES">
In this mode, agents must request approval before making any change to the filesystem or running any command. AI Forge surfaces a confirmation prompt in the chatroom for every proposed action, showing you exactly what will be modified before anything happens.

**When to use it:** During active development on critical branches, when onboarding a new agent whose behavior you haven't fully validated, or any time you want a human in the loop before code changes land.

**Trade-off:** Every action requires a manual confirmation click, which slows down highly autonomous workflows.
</Accordion>

<Accordion title="AUTO_APPLY">
In this mode, agents apply file changes and execute commands immediately without waiting for your approval. Actions still appear in the activity feed so you can review what was done, and all changes are logged.

**When to use it:** When you trust the agents in your project and want maximum throughput — for example, during a well-defined, low-risk task like reformatting code or updating dependency versions.

**Trade-off:** Mistakes are applied instantly. If an agent makes an incorrect change, you will need to revert it manually or via version control.
</Accordion>

<Accordion title="SAFE_MODE">
SAFE_MODE is the most restrictive execution mode. It blocks all destructive operations project-wide — no file deletions, no command execution, and no package installations — regardless of what individual agent flags say. Agents can still read files and propose changes, but nothing irreversible can happen without you manually disabling SAFE_MODE first.

**When to use it:** When experimenting with an unfamiliar or community-sourced agent, when you want to audit what an agent *would* do before letting it act, or as a default for sensitive repositories.

**Trade-off:** Agents that rely on running commands (e.g. a build agent or test runner) will be unable to complete their tasks until you raise the execution mode.
</Accordion>

## Credential Isolation

When you store a provider API key in AI Forge, it is saved server-side — either as an environment variable or in an encrypted keystore. **Credentials are never returned to the browser after storage.** The key is used by the server to authenticate requests on your behalf; at no point does it travel back to the frontend or appear in agent messages.

This design ensures that even if an agent attempted to exfiltrate credentials by asking the server to echo them, the server would have no mechanism to fulfill that request. The credential lives only in the server-side secure storage layer and is injected directly into outbound API calls.

<Note>
If you need to rotate a key, add the new credential in **Settings → Providers**, then delete the old one. Agents will automatically use the updated credential on their next request.
</Note>
